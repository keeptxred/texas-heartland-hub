# Explore Texas Canonical Data Model

Status: Phase I, Step 2A
Visibility: Internal architecture only
Public routes: None

## Purpose

The canonical data model is the contract shared by the database, APIs, search, planner, PDF generation, advertisements, and future mobile clients. Each fact has one authoritative owner and may be consumed by many features.

## Core rules

1. Every recordable object is an entity.
2. Every entity has an immutable internal identifier.
3. Public slugs are mutable presentation identifiers and never replace internal IDs.
4. Relationships are first-class records with their own metadata.
5. Time-varying facts are stored as observations, not destructive updates.
6. Verified factual data is separated from generated narrative content.
7. Production records are archived rather than hard-deleted.
8. Every publishable fact must retain source provenance.

## Universal entity contract

All entity types inherit the following fields:

| Field | Type | Required | Rule |
|---|---|---:|---|
| id | UUID | Yes | Immutable primary key |
| entity_type_id | UUID | Yes | References entity type catalog |
| lifecycle_status | Enum | Yes | Draft, imported, validated, reviewed, published, verified, archived |
| name | Text | Yes | Canonical display name |
| slug | Text | Conditional | Required before publication; unique among public entities |
| short_description | Text | Optional | Search and card summary |
| long_description | Text | Optional | Verified long-form description |
| visibility | Enum | Yes | Internal, private, unlisted, public |
| featured | Boolean | Yes | Defaults false |
| popularity_score | Numeric | Yes | Defaults zero; derived, not editorial truth |
| confidence_score | Numeric | Yes | 0–100 |
| owner_id | UUID | Optional | Responsible editor, team, agency, or importer |
| created_at | Timestamp | Yes | Immutable creation time |
| updated_at | Timestamp | Yes | Last material update |
| published_at | Timestamp | Optional | Set on first publication |
| verified_at | Timestamp | Optional | Last factual verification |
| archived_at | Timestamp | Optional | Set when archived |
| current_version | Integer | Yes | Starts at 1 |

## Entity lifecycle

Allowed forward progression:

Draft → Imported → Validated → Reviewed → Published → Verified → Archived

Allowed corrective transitions:

- Imported → Draft
- Validated → Draft
- Reviewed → Validated
- Published → Reviewed
- Verified → Reviewed
- Archived → Reviewed

No lifecycle transition may bypass validation. Public visibility requires at least Reviewed status. Verified status requires a verification record and at least one authoritative source.

## Entity identity

Internal IDs are UUIDs generated by PostgreSQL and never exposed as the primary public URL contract. Human-readable slugs may change. A slug-history table preserves redirects after publication.

External identifiers are stored separately by source namespace, for example:

- TPWD park ID
- NPS unit code
- USGS feature ID
- County FIPS code
- GNIS ID

External identifiers never become internal primary keys.

## Ownership of facts

A fact belongs to the entity whose meaning it describes.

Examples:

- Fish owns scientific name, taxonomy, typical length, and spawning information.
- Lake owns surface acreage, shoreline length, and maximum depth.
- The Lake–Fish relationship owns abundance, best months, stocking notes, and fishing relevance.
- Campground owns check-in rules and site inventory.
- The Campground–Amenity relationship owns availability, seasonality, quantity, and accessibility details.

## Relationship contract

Every relationship stores:

| Field | Required | Description |
|---|---:|---|
| id | Yes | Immutable UUID |
| source_entity_id | Yes | Directed origin |
| relationship_type_id | Yes | Cataloged relationship type |
| target_entity_id | Yes | Directed destination |
| status | Yes | Draft, active, inactive, archived |
| strength | Optional | Primary, direct, nearby, regional, suggested |
| confidence_score | Yes | 0–100 |
| distance_miles | Optional | Straight-line or documented distance |
| travel_time_minutes | Optional | Mode-dependent estimate |
| travel_mode | Optional | Drive, walk, boat, bike, trail |
| valid_from | Optional | Effective date/time |
| valid_through | Optional | Expiration date/time |
| seasonal | Yes | Defaults false |
| metadata | Optional | Typed JSON for relationship-specific attributes |
| verified_at | Optional | Last verification |
| created_at | Yes | Creation timestamp |
| updated_at | Yes | Last material update |

Duplicate active relationships with the same source, type, target, and validity window are prohibited.

## Time-aware information

Mutable operational facts use observations:

- Water level
- Water clarity
- Weather
- Burn bans
- Closures
- Park hours
- Fees
- Fishing reports
- Wildlife sightings
- Bloom conditions

Each observation includes entity, observation type, value, unit, observed time, effective window, source, confidence, and expiration behavior. Historical observations are retained.

## Immutable and correction-controlled fields

The following are immutable after creation except through an audited correction workflow:

- Internal UUID
- Entity creation timestamp
- Source record identity
- Observation timestamp
- Version record identity

Stable official identifiers such as county FIPS and scientific taxonomy identifiers are correction-controlled rather than casually editable.

## Versioning and audit

Every material entity change creates an entity version containing a complete JSON snapshot, change reason, actor, source context, and timestamp. Relationship changes are audited separately. Rollback creates a new version; it does not erase intervening history.

## Provenance and confidence

Recommended baseline confidence values:

| Source class | Baseline |
|---|---:|
| Official government source | 100 |
| Verified Keep TX Red editor | 95 |
| Contracted or recognized partner | 90 |
| Community submission independently verified | 80 |
| Unverified community submission | 60 |
| AI-generated inference | 40 maximum |

Confidence may be reduced for stale, conflicting, incomplete, or indirectly derived data. AI-generated text cannot be the sole source for a verified factual field.

## Media model

Media assets are independent records. Entity-media relationships determine usage and role:

- Hero
- Gallery
- Map
- Trail map
- Diagram
- Thumbnail
- PDF illustration
- Advertisement creative

The relationship stores caption, alt text, credit, rights, sort order, crop metadata, and validity dates.

## Taxonomy and tags

Entity type answers what an entity is. Taxonomy describes structured classification. Tags support lightweight editorial discovery.

Example:

Largemouth Bass
- Entity type: Fish
- Taxonomies: Freshwater, Game Fish, Native Status
- Tags: Popular, Beginner Friendly, Trophy Fishing

Tags may not replace fields required for filtering, law application, publication gates, or planner logic.

## Geography

Geography supports hierarchy and overlap:

Texas → Region → County → City or Community → Destination → Facility

Destinations may belong to multiple counties and regions. Geographic membership uses relationships and optional geospatial geometry rather than a single county column.

## Generated content separation

Verified data and generated narrative are stored independently.

Generated content records include:

- Entity or trip context
- Content purpose
- Model and prompt version
- Generated text
- Review status
- Source fact snapshot
- Generated timestamp
- Expiration or regeneration policy

Generated content may be displayed only when permitted by review and visibility rules. Regeneration never mutates verified facts.

## Publication gates

All public entities require:

- Canonical name
- Valid entity type
- Public slug
- Public visibility
- Valid location or geographic scope when applicable
- At least one active source attribution
- Reviewed lifecycle status or higher
- No blocking validation errors
- Required type-specific fields

Example Lake publication requirements:

- Name
- Coordinates or mapped geometry
- At least one county relationship
- Managing agency when known and officially documented
- Verified source
- Summary description
- Operational status

A hero image is recommended but is not a universal hard requirement because rights-cleared media may not yet be available.

## Feature consumption

| Consumer | Canonical inputs |
|---|---|
| Search | Entity names, aliases, types, geography, activities, amenities, taxonomy, relationship text |
| Destination pages | Entity facts, media, relationships, observations, sources |
| Planner | Activities, suitability, geography, facilities, laws, seasonality, businesses, safety |
| PDFs | Planner output plus verified facts, media rights, maps, emergency contacts, citations |
| Advertisements | Geography, activity context, audience suitability, business category, sponsorship status |
| AI assistant | Verified fact snapshot, relationship graph, current observations, citations |

## Non-public implementation rule

Completion of this model does not authorize any route, navigation entry, sitemap entry, public query policy, or public API. All implementation remains internal until a separate launch approval is recorded.
