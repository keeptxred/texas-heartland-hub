# Explore Texas Physical Database Design

Status: Phase I, Step 2B
Target: PostgreSQL through Supabase
Visibility: Internal architecture only
Public routes: None

## Objective

Translate the canonical data model into a normalized PostgreSQL design that supports destinations, geography, species, activities, amenities, laws, media, provenance, search, planner logic, PDFs, and context-aware advertising.

This document defines the initial table families, constraints, indexing strategy, row-level security posture, archival behavior, and migration sequence. It does not create public pages or public data access.

## Database principles

1. Use UUID primary keys generated by PostgreSQL.
2. Keep universal entity identity separate from type-specific attributes.
3. Use foreign keys for structural integrity and JSONB only for bounded extensibility.
4. Represent many-to-many connections through explicit relationship records.
5. Store time-varying values as append-only observations.
6. Preserve provenance at fact, relationship, observation, and media levels.
7. Prefer partial and composite indexes based on real query paths.
8. Enable RLS before data is inserted; default to no anonymous access.
9. Use soft archival for production records.
10. Keep generated content outside verified factual columns.

## Recommended schemas

Use a dedicated PostgreSQL schema to avoid collisions with existing application tables:

```sql
create schema if not exists explore_texas;
```

Application-facing RPCs or views may later be exposed through `public`, but the base tables remain in `explore_texas`.

## PostgreSQL extensions

Recommended:

```sql
create extension if not exists pgcrypto;
create extension if not exists pg_trgm;
create extension if not exists postgis;
```

PostGIS is recommended for points, polygons, distance searches, and route-adjacent filtering. If the deployed Supabase project cannot enable PostGIS immediately, geography columns may be introduced in a later migration without changing entity identity.

## Enumerations

Initial database enums:

```text
entity_lifecycle_status:
  draft, imported, validated, reviewed, published, verified, archived

entity_visibility:
  internal, private, unlisted, public

relationship_status:
  draft, active, inactive, archived

relationship_strength:
  primary, direct, nearby, regional, suggested

source_class:
  official_government, verified_editor, recognized_partner,
  verified_community, unverified_community, ai_generated

review_status:
  pending, approved, rejected, needs_revision

media_kind:
  image, video, audio, document, map, gpx, kml, panorama

observation_value_type:
  text, number, boolean, date, timestamp, json
```

Enums should be used only for stable platform concepts. Editorial classifications belong in catalog tables.

# Core table families

## 1. Entity catalog

### `explore_texas.entity_types`

Defines stable types such as lake, state park, campground, fish, bird, wildflower, agency, business, law, and facility.

Key columns:

```text
id uuid primary key
code text unique not null
name text not null
description text
parent_type_id uuid nullable references entity_types
is_destination boolean not null default false
is_species boolean not null default false
is_geographic boolean not null default false
is_business boolean not null default false
is_active boolean not null default true
created_at timestamptz not null
updated_at timestamptz not null
```

### `explore_texas.entities`

Universal identity and publication state.

```text
id uuid primary key default gen_random_uuid()
entity_type_id uuid not null references entity_types
lifecycle_status entity_lifecycle_status not null default 'draft'
visibility entity_visibility not null default 'internal'
name text not null
slug text
short_description text
long_description text
featured boolean not null default false
popularity_score numeric(12,4) not null default 0
confidence_score numeric(5,2) not null default 0 check 0..100
owner_user_id uuid nullable
current_version integer not null default 1
created_at timestamptz not null default now()
updated_at timestamptz not null default now()
published_at timestamptz
verified_at timestamptz
archived_at timestamptz
```

Constraints:

- Public entities require a slug.
- Archived entities require `archived_at`.
- Slugs are unique among non-archived records.
- Confidence remains between 0 and 100.

Recommended indexes:

```text
(entity_type_id, lifecycle_status)
(visibility, lifecycle_status)
partial unique lower(slug) where archived_at is null and slug is not null
GIN name/description search vector
trigram lower(name)
```

### `explore_texas.entity_aliases`

Stores alternate names, former names, abbreviations, and spelling variants.

```text
id uuid primary key
entity_id uuid not null references entities
alias text not null
alias_type text not null
language_code text not null default 'en'
is_searchable boolean not null default true
source_id uuid nullable
created_at timestamptz not null
```

Unique key: `(entity_id, lower(alias), alias_type)`.

### `explore_texas.entity_slug_history`

Preserves redirects after public slug changes.

```text
id uuid primary key
entity_id uuid not null references entities
old_slug text not null
replaced_at timestamptz not null
redirect_active boolean not null default true
```

## 2. Type-specific profile tables

Universal identity stays in `entities`; structured domain fields live in one-to-one profile tables.

Initial profiles:

- `geographic_profiles`
- `destination_profiles`
- `lake_profiles`
- `park_profiles`
- `campground_profiles`
- `historic_site_profiles`
- `species_profiles`
- `business_profiles`
- `agency_profiles`
- `law_profiles`
- `facility_profiles`

Each profile uses `entity_id` as both primary key and foreign key to `entities`, enforcing one profile per entity.

Example `lake_profiles`:

```text
entity_id uuid primary key references entities
surface_acres numeric
shoreline_miles numeric
maximum_depth_feet numeric
average_depth_feet numeric
reservoir_type text
primary_use text
impoundment_year integer
waterbody_status text
```

Example `species_profiles`:

```text
entity_id uuid primary key references entities
scientific_name text
family_name text
conservation_status text
native_status text
identification_summary text
safety_summary text
```

Profile checks should reject negative acreage, depth, distance, capacity, or fee values.

## 3. Geography

### `explore_texas.geographies`

Stores point and boundary data for geographic entities and destinations.

```text
entity_id uuid primary key references entities
centroid geography(Point, 4326)
boundary geography(MultiPolygon, 4326)
elevation_feet numeric
timezone text
county_fips text
state_fips text
geocoding_precision text
```

Not every geography requires both centroid and boundary, but publishable physical destinations require at least one valid spatial representation or an approved exception.

Spatial indexes:

```text
GIST centroid
GIST boundary
```

Geographic hierarchy remains relationship-driven so a destination can occupy multiple counties.

## 4. Relationship engine

### `explore_texas.relationship_types`

```text
id uuid primary key
code text unique not null
name text not null
inverse_code text
source_type_rule jsonb
target_type_rule jsonb
is_symmetric boolean not null default false
allows_multiple boolean not null default true
requires_source boolean not null default true
requires_verification boolean not null default false
is_active boolean not null default true
```

### `explore_texas.entity_relationships`

```text
id uuid primary key default gen_random_uuid()
source_entity_id uuid not null references entities
target_entity_id uuid not null references entities
relationship_type_id uuid not null references relationship_types
status relationship_status not null default 'draft'
strength relationship_strength
confidence_score numeric(5,2) not null default 0 check 0..100
distance_miles numeric
travel_time_minutes integer
travel_mode text
seasonal boolean not null default false
valid_from timestamptz
valid_through timestamptz
metadata jsonb not null default '{}'
verified_at timestamptz
created_at timestamptz not null default now()
updated_at timestamptz not null default now()
archived_at timestamptz
```

Checks:

- Source and target cannot be equal unless explicitly allowed by relationship type.
- Distances and travel times cannot be negative.
- `valid_through` must be later than `valid_from`.
- Archived status requires `archived_at`.

Uniqueness:

A partial unique index prevents duplicate active relationships across source, type, target, and normalized validity window.

Query indexes:

```text
(source_entity_id, relationship_type_id, status)
(target_entity_id, relationship_type_id, status)
(source_entity_id, target_entity_id)
GIN metadata
```

## 5. Sources and provenance

### `explore_texas.sources`

Represents organizations, documents, datasets, pages, APIs, and firsthand verification records.

```text

license text

published_at timestamptz
expires_at timestamptz
content_hash text

is_active boolean not null default true
metadata jsonb not null default '{}'
```

### `explore_texas.entity_sources`

```text
entity_id uuid not null references entities
source_id uuid not null references sources
source_role text not null
supports_fields text[]
notes text
verified_at timestamptz
primary key (entity_id, source_id, source_role)
```

### `explore_texas.relationship_sources`

Equivalent provenance mapping for relationships.

### `explore_texas.fact_assertions`

Optional fine-grained provenance table for important facts.

```text
id uuid primary key
entity_id uuid not null
field_path text not null
asserted_value jsonb not null
source_id uuid not null
confidence_score numeric(5,2) not null
valid_from timestamptz
valid_through timestamptz
review_status review_status not null default 'pending'
```

This table is recommended for laws, fees, hours, measurements, and disputed facts, but not required for every descriptive sentence in the first release.

## 6. Observations

### `explore_texas.observation_types`

Catalogs water level, closure, bloom status, bird sighting, fishing report, burn ban, fee, and hours observations.

### `explore_texas.observations`

Append-only time-aware values.

```text
id uuid primary key
entity_id uuid not null references entities
observation_type_id uuid not null references observation_types
value_type observation_value_type not null
value_text text
value_number numeric
value_boolean boolean
value_date date
value_timestamp timestamptz
value_json jsonb
unit text
observed_at timestamptz not null
effective_from timestamptz
effective_through timestamptz
source_id uuid not null references sources
confidence_score numeric(5,2) not null
created_at timestamptz not null default now()
```

A constraint ensures exactly one value column is populated according to `value_type`.

Indexes:

```text
(entity_id, observation_type_id, observed_at desc)
(observation_type_id, effective_from, effective_through)
BRIN observed_at for high-volume history
```

Partitioning is unnecessary initially. Add time partitioning only after observation volume justifies operational complexity.

## 7. Taxonomy, categories, tags

Tables:

- `taxonomies`
- `taxonomy_terms`
- `entity_taxonomy_terms`
- `tags`
- `entity_tags`

Taxonomy terms support parent-child hierarchy. Tag assignments include source, confidence, and editorial status to prevent uncontrolled AI tagging from becoming authoritative.

## 8. Activities and amenities

Activities and amenities are modeled as entities so they can have descriptions, media, rules, sources, and relationships.

Relationship examples:

- Destination `supports` Activity
- Destination `has_amenity` Amenity
- Facility `provides` Amenity
- Activity `requires` Equipment
- Law `applies_to` Activity

Relationship metadata supports:

- Suitability level
- Accessibility
- Quantity
- Availability
- Seasonality
- Cost
- Reservation requirement
- Skill level

Avoid separate boolean columns such as `has_restrooms` or `allows_fishing` on every destination table.

## 10. Laws and regulations

Laws and regulations remain entities with `law_profiles` containing:

- Jurisdiction
- Issuing authority
- Citation or code reference
- Effective date
- Expiration or repeal date
- Official URL
- Summary
- Compliance notes

Relationships apply laws to activities, entity types, geographic areas, or specific destinations. More specific relationships override broader rules only when explicitly marked with precedence metadata and verified sources.

## 11. Businesses and advertisements

Business records remain factual entities. Sponsorship and advertising are separate commercial records.

Recommended commercial tables:

- `advertisers`
- `campaigns`
- `placements`
- `campaign_target_rules`
- `sponsorship_relationships`
- `ad_impressions`
- `ad_clicks`

Campaign targeting may reference geography, destination, activity, audience context, or business category. Paid placement must never alter factual ranking fields or verification confidence.

## 12. Planner and PDF data

Planner sessions should not mutate source entities.

Recommended tables:

- `planner_sessions`
- `planner_preferences`
- `planner_destinations`
- `planner_recommendations`
- `planner_exports`

A generated plan records the canonical entity version and observation cutoff used so a PDF can later explain when its facts were current.

PDF exports store:

- Planner session ID
- Template version
- Entity/version snapshot references
- Generation timestamp
- Expiration warning date
- Storage key
- Branding variant
- Included advertisement placements

## 13. Generated content

Tables:

### `explore_texas.generated_content`

id uuid primary key
entity_id uuid nullable

purpose text not null
model_identifier text not null

## 14. Version and audit tables

### `entity_versions`

Stores complete snapshots after material changes.

### `relationship_versions`

Stores relationship snapshots.

### `audit_events`

Stores actor, action, table family, record ID, request context, before/after summary, and timestamp.

Audit tables should be append-only to normal application roles.

## Search architecture

Initial search can use PostgreSQL full-text search plus trigram similarity.

Recommended materialized or maintained search document:

### `explore_texas.entity_search_documents`

```text
entity_id uuid primary key
search_vector tsvector not null
normalized_name text not null
search_text text not null
entity_type_code text not null
geography_text text
activity_text text
amenity_text text
taxonomy_text text
popularity_score numeric not null
updated_at timestamptz not null
```

The search document is rebuilt when entities, aliases, selected relationships, or taxonomies change. It is derivative and may be recreated from canonical data.

Search rank combines:

1. Exact canonical-name match
2. Alias match
3. Entity-type relevance
4. Geographic relevance
5. Activity and amenity relevance
6. Full-text rank
7. Trigram similarity
8. Editorial quality and verification state
9. Popularity as a modest tie-breaker

Paid advertising must not modify organic search rank.

## Row-level security posture

All base tables must have RLS enabled before production data is loaded.

Initial policy posture:

- Anonymous: no access
- Authenticated general user: no base-table access
- Internal editorial role: read draft and reviewed records; scoped writes
- Reviewer role: approve validation and verification transitions
- Import service role: insert imported records and observations, but not publish
- Server service role: controlled access for internal APIs

Future public access should use reviewed views or RPCs that expose only public, non-archived, rights-cleared data. Do not grant anonymous `select` directly on base tables.

## Delete and archival behavior

- Entities: archive; do not delete after references or versions exist.
- Relationships: mark inactive or archived.
- Sources: deactivate; preserve citations.
- Observations: append-only; corrections create superseding records.
- Media: archive metadata before deleting physical storage; retain rights and audit history.
- Planner sessions: may be deleted under privacy/retention rules, while anonymized aggregate metrics may remain.
- Advertisement events: retained according to documented analytics retention policy.

Foreign keys should normally use `ON DELETE RESTRICT`. Draft-only orphan records may be removed through explicit administrative cleanup procedures before publication.

## Initial indexing strategy

Create indexes only for expected query paths:

- Public/review lifecycle filtering
- Entity type and status
- Name and alias lookup
- Outbound and inbound relationship traversal
- Spatial proximity
- Current observations by entity/type
- Source provenance lookup
- Taxonomy and tag membership
- Media role ordering
- Planner-session ownership

Avoid premature indexes on low-selectivity booleans unless used in a partial index.

## Migration sequence

Recommended implementation order:

1. Create schema, extensions, and enums.
2. Create entity types and entities.
3. Create aliases, slug history, versions, and audit events.
4. Create source and provenance tables.
5. Create relationship type and relationship tables.
6. Create geography and profile tables.
7. Create taxonomy and tag tables.
8. Create observation tables.
9. Create media tables.
10. Create generated-content tables.
11. Create planner and export tables.
12. Create advertising tables.
13. Add indexes and validation triggers.
14. Enable RLS and internal policies.
15. Seed controlled catalogs.
16. Add internal-only validation views.

Each migration must be reversible where PostgreSQL safely permits it. Destructive rollback of populated canonical tables is prohibited outside disposable environments.

## Phase I implementation boundary

Step 2B authorizes schema and migration preparation only. It does not authorize:

- Public routes
- Explore Texas navigation
- Sitemap additions
- Anonymous database policies
- Public APIs
- Published destination pages
- Live planner access
- Public PDFs
- Paid advertisement delivery

## Acceptance criteria

The physical design is ready for migration implementation when:

- Every canonical entity maps to `entities` plus an appropriate profile or relationship.
- Every many-to-many association maps to explicit relationships or a dedicated junction table.
- Mutable facts use observations or effective-dated assertions.
- Provenance can be traced for entities, relationships, and observations.
- Archival behavior is defined.
- RLS defaults to deny public access.
- Search documents are derivative, not authoritative.
- AI-generated content cannot mutate verified facts.
- The planner and PDF engine can reference entity versions and observation cutoffs.
